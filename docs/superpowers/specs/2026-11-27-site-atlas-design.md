# Атлас сайтов и граф компаний: дизайн

Дата: 2026-11-27
Статус: ждёт одобрения владельца.
Это первый этап перед `2026-11-27-model-archive-design.md` («дизайн архива»). Конфиги брендов для архива берутся из атласа.

## Зачем это нужно

Владелец (его слова): «до того как начать scraping нужна система, что сохранять, чтобы было как можно больше данных и связей между компаниями и сайтами. Агент описывает, как сайт работает, где какие ссылки, как соединён с другими сайтами, чтобы другой агент не начинал всё с нуля. То есть сохранять больше, а в базу записывать основное, что мы сейчас решили».

Сейчас каждый агент, который настраивает скрапер бренда, заново выясняет устройство сайта:
- где каталог;
- где поддержка;
- где лежат PDF;
- нужен ли рендер;
- куда ведут редиректы.

Эти знания нигде не остаются. История страниц тоже теряется: `.cache/pages` хранит одну копию на URL, и `--refresh` её перезаписывает. Связи между компаниями сведены к строке `group` в конфиге бренда.

## Цели

- **Сырые данные копятся, а не перезаписываются.** Каждая загруженная версия страницы или PDF хранится локально, с журналом загрузок.
- **Атлас сайтов** — описание каждого сайта для следующего агента:
  - как сайт устроен;
  - где каталог, поддержка, документы и ссылки на приложения;
  - что требует рендера, что запрещает `robots.txt`;
  - какие редиректы на нём есть;
  - с какими сайтами он связан;
  - что есть по нему в Web Archive.
- **Предложение конфига скрапера** для каждого бренда. Оно составляется по атласу и одобряется владельцем.
- **Граф компаний и сайтов:** кто кем владеет, кто для кого делает аппараты, какие домены и приложения у кого, какие имена заявителей в FDA.
  - Часть связей публикуется на сайте (решение владельца).
- **В публичную базу (`data/models`, `data/reviews`, брендовые поля) попадает только то, что решено в основном дизайне и дизайне архива (решение владельца).** Атлас и граф — отдельный слой.

## Чего не делаем

- Не кладём в git сырые страницы и PDF. Репозиторий на GitHub публичный, и это было бы распространение чужих материалов. Сырые данные хранятся только локально.
- Агент не ходит в сеть сам. Все загрузки идут через наш загрузчик: честный User-Agent, `robots.txt`, паузы, без обхода защиты. Своих браузеров и сетевых инструментов у агента нет.
- Не обходим сайт целиком. У каждого сайта бюджет страниц, а остальное известно из `sitemap.xml` без загрузки.
- Не публикуем непроверенные связи. На сайт попадает только связь с источником, одобренная в `/review`.
- Не скрапим сайты магазинов и обзоров ради атласа. Ссылки на них только учитываются как исходящие.

## Чем это не должно стать

- Описания, которые агент выдумал, а не увидел. У каждого утверждения в описании должна быть ссылка на страницу из журнала загрузок.
- Сотни непрочитанных файлов. Атлас ценен, только если следующий агент находит нужное за минуту, поэтому у него есть оглавление и единый формат.
- Публичная связь вида «X делает аппараты для Y» без первоисточника. Это юридический риск.

## Рассмотренные подходы

- **A. Агент-исследователь на каждый сайт.**
  - Плюс: глубокое понимание.
  - Минусы: тратит лимиты, результат каждый раз немного разный, медленно.
- **B. Только код.**
  - Плюсы: воспроизводимо и дёшево.
  - Минус: код не понимает назначения разделов.
- **C. Смешанный.** *Выбран владельцем.* Код собирает механические факты и граф ссылок. Агент читает этот отчёт и несколько ключевых страниц, потом пишет описание, предложение конфига и связи с источниками.

## Что решено

Решения владельца отмечены. Остальное — мои решения, их можно поправить.

### 1. Хранилище сырых данных (только локально)

- **`.cache/raw/<sha256 тела>`** — тело ответа: HTML, PDF, JSON. Одинаковое содержимое хранится один раз. Файлы никогда не перезаписываются и не удаляются конвейером.
- **`.cache/raw/log.jsonl`** — журнал загрузок, только дописывается. Одна строка на загрузку:
  - `url`, `finalUrl`, цепочка редиректов;
  - `fetchedAt`, HTTP-статус, `contentType`;
  - хэш тела;
  - `via`: `live` или `archive` (копия Web Archive);
  - `rendered`;
  - для пропусков: причина (`robots`, `blocklist`, `bot-protection`, `429`…).
- Загрузчик пишет туда каждую сетевую загрузку. `.cache/pages` остаётся как быстрый индекс «последняя версия URL», и `--refresh` больше ничего не теряет.
- Резервная копия на совести владельца (Time Machine и т. п.). Ожидаемый объём — единицы гигабайт.

### 2. Атлас сайтов (`data/atlas/`, в git)

**Какие сайты входят:**
- сайт каждого бренда;
- корпоративные сайты групп (Sonova, Demant, WS Audiology, GN, Starkey и т. д.);
- домены, где бренды хранят документы или приложения, если они найдены в отчётах;
- сайты ушедших брендов, собранные по копиям Web Archive.

Для каждого сайта есть папка `data/atlas/sites/<домен>/`.

#### Шаг кода `npm run atlas:crawl -- --site <домен>` → `report.json`

Отчёт собирает только механические факты, без LLM:
- **`robots.txt`:** правила, `Crawl-delay`, объявленные sitemap.
- **`sitemap.xml`** и индекс sitemap: число URL по разделам первого уровня. Это список, страницы по нему не загружаются.
- **Обход в ширину** с главной страницы и разделов sitemap, через загрузчик, в пределах бюджета (`config.atlas.pageBudget`, по умолчанию 60 страниц на сайт). По каждой странице:
  - заголовок;
  - ссылки внутренние и внешние;
  - ссылки на PDF;
  - ссылки на App Store и Google Play;
  - типы JSON-LD;
  - признак «нужен рендер»: в HTML мало текста при большом объёме скриптов.
- **Шаблоны URL:** похожие пути сгруппированы, например `/hearing-aids/{slug}` (42 URL).
- **Исходящие домены** с числом ссылок и примерами, редиректы, хосты PDF.
- **Покрытие Web Archive:** по ключевым разделам число копий по годам с 2018, через CDX API.
- **Что не удалось загрузить** и почему.

Каждый факт в отчёте ссылается на строку журнала загрузок (`url` + `fetchedAt`). Отчёт кладётся в git: это факты о структуре сайта, а не его содержимое.

#### Шаг агента `npm run atlas:describe -- --site <домен>`

Работает через `claude -p` со строгой JSON-схемой и без сетевых инструментов.
- **На вход:** `report.json` и выдержки текста 5–8 ключевых страниц, выбранных кодом: главная, кандидаты в каталог, кандидаты в поддержку, одна страница модели, одна страница со списком PDF.
- **Дозапрос:** агент может попросить ещё до 10 URL, не больше двух раундов. Код загружает их через загрузчик.
- **На выход:**
  - `README.md` — описание сайта в едином формате. Разделы:
    - что это за сайт и чей он;
    - структура;
    - где каталог, поддержка, документы и приложения;
    - рендер и особенности;
    - связи с другими сайтами;
    - Web Archive;
    - что проверить следующему агенту.
    У каждого утверждения ссылка на загруженную страницу.
  - `config-proposal.json` — предложение конфига бренда: `catalogUrls`, `supportUrls`, `modelUrlPattern`, `documentUrlPattern`, `render`, `archive.catalogUrls`, `status`.
  - **Предложения связей** для графа (см. ниже).
- **Проверки кодом:**
  - каждая ссылка-источник в описании есть в журнале загрузок;
  - каждый шаблон URL из предложения конфига совпадает хотя бы с одним URL отчёта;
  - цитаты к связям буквально есть в тексте источника.
- **Модель:** `config.llm.describeModel`, по умолчанию `sonnet`. Описание делается редко, раз на сайт, и от его качества зависят все следующие агенты.

#### `data/atlas/README.md` — оглавление

По каждому сайту:
- дата отчёта и описания;
- статус бренда;
- одна строка о главном;
- открытые вопросы.

Отдельный раздел «как обновить атлас» для следующего агента.

#### `notes.md` в папке сайта

Дополняемый журнал для агентов: что пробовали, что не сработало, с датой. Его ведёт любой агент, который работает с этим сайтом, в том числе исполнитель скрапера. Это и есть защита от «начинать с нуля».

**Конфиг бренда меняется только через `/review`:** предложение идёт в `pending/` как новый вид `brand-config` и показывается как разница «было → стало» с ссылками на отчёт. Одобрение записывает его в `data/brands/<brand>.json`.

### 3. Граф компаний и сайтов (`data/graph/`, в git)

**`entities.json`** — узлы `{ id, kind, name }`. Виды:
- `company` — юридическое лицо, группа;
- `brand`;
- `domain`;
- `app` — приложение с `iosId` и `androidId`;
- `fda-applicant` — имя заявителя в записях 510(k);
- `sec-filer` — CIK.

**`edges.json`** — связи `{ from, to, kind, since?, until?, visibility, status, sources }`.
- **Виды:**
  - `owns` — компания владеет брендом или компанией;
  - `makes-for` — производитель делает аппараты бренда;
  - `operates` — бренд или компания управляет доменом;
  - `publishes` — бренд выпускает приложение;
  - `files-as` — бренд или компания подаёт в FDA под этим именем;
  - `renamed-to`;
  - `redirects-to`, `links-to`, `hosts-documents-for` — между доменами.
- **`visibility`:**
  - `public` — может появиться на сайте;
  - `internal` — только для агентов.
- **`status`:**
  - `observed` — связь увидел код в журнале загрузок: редирект, ссылка, PDF на чужом хосте;
  - `proposed` — предложил агент, связь не проверена;
  - `verified` — одобрена владельцем.
- **`sources`:** `{ url, quote?, fetchedAt }`.

**Кто что пишет:**
- **Код** записывает доменные связи (`redirects-to`, `links-to`, `hosts-documents-for`) сразу, как `internal`/`observed`. Источник — строка журнала.
- **Агент** записывает связи между компаниями, брендами и приложениями как `proposed`. Это помогает следующему агенту, но на сайт такие связи не попадают.
- **На сайт** связь попадает только через `/review` (новый вид `relation`). Для этого нужен первоисточник с цитатой, прошедшей проверку на буквальное совпадение:
  - официальная страница компании;
  - пресс-релиз;
  - отчёт в SEC;
  - запись FDA;
  - для `makes-for` это может быть и источник третьей стороны, с подписью «по данным <источник>», как у «того же железа».
  После одобрения связь получает `public`/`verified`.

`brand.group` остаётся в конфиге бренда. Проверка в тестах сравнивает его с одобренной связью `owns` и сообщает о расхождении.

### 4. Что видно на сайте

- **На странице бренда блок «Company»** с одобренными связями:
  - кому принадлежит и с какого года;
  - родственные бренды той же группы;
  - кто делает аппараты (`makes-for`), с подписью источника;
  - приложение.
- **Новая страница `/companies`** — «Who owns which hearing aid brand»: группы, их бренды и ссылки на источники. Она полезна для SEO и проверяется так же, как характеристики.
- Связи `internal` и `proposed` на сайт не попадают никогда.

### 5. Порядок работы

1. **Хранилище сырых данных** (изменение загрузчика).
2. **`atlas:crawl`** по всем сайтам из списка. Это автоматически, порядка 4–5 минут на сайт из-за пауз.
3. **`atlas:describe`** по каждому сайту. Предложения конфигов и связей уходят в `/review`.
4. **Владелец одобряет конфиги и связи.** По оценке, 1–2 минуты на бренд и полминуты на связь.
5. **Только после этого** запускаются скрапинг и архив старых моделей по дизайну архива, по уже одобренным конфигам. Исполнитель скрапера читает `README.md` и `notes.md` сайта, а то, что узнал сам, дописывает в `notes.md`.

## Что остаётся на усмотрение исполнителя

- Точные схемы `report.json`, `entities.json` и `edges.json`.
- Алгоритм группировки URL в шаблоны.
- Как выбирать ключевые страницы для агента.
- Вёрстка блока «Company» и страницы `/companies`.
- Тесты. Обязательно должны быть тесты:
  - что сырое хранилище не перезаписывает тело и дописывает журнал;
  - что шаблоны из предложения конфига проверяются по отчёту;
  - что связь без одобрения не попадает на сайт;
  - что ссылка-источник, которой нет в журнале, отклоняется.

## Решения, принятые при проверке дизайна (*мои*, проверьте при чтении)

1. **Источники для связей ищет отдельный шаг `atlas:relations`.**
   - Поиск идёт через `claude -p` с WebSearch, так же, как конвейер уже ищет сторонние цены и обзоры. Google мы при этом сами не скрапим.
   - Найденные URL загружает наш загрузчик, цитаты проверяет код.
   - Код также заполняет узлы `sec-filer` (поиск компании в SEC EDGAR, User-Agent с `NEXT_PUBLIC_CONTACT_EMAIL`, без него шаг пропускается) и `fda-applicant` (имена заявителей из 510(k) по нашим кодам продуктов).
   - У шага `atlas:describe` сети по-прежнему нет.
2. **Этап атласа сам меняет схему бренда и проводит миграцию:**
   - `datasheetUrlPattern` → `documentUrlPattern`;
   - новые поля `supportUrls`, `archive`, `status`.
   - `scrape` сразу читает `supportUrls` как источник документов, как сейчас читает страницы поддержки в `catalogUrls`, так что перенос страниц ничего не ломает.
   - Бренд со статусом `gone` сразу перестаёт скрапиться вживую.
   - Одобрение предложения в `/review` пишет `data/brands/` сразу.
3. **Список сайтов задаётся вручную в `data/atlas/sites.json`.**
   - Что в нём: сайты всех брендов, корпоративные сайты групп (Sonova, Demant, WS Audiology, GN, Starkey и материнские компании OTC-брендов) и ушедшие бренды.
   - Новые домены из отчётов не обходятся автоматически. Они попадают в оглавление как кандидаты, а в `sites.json` их добавляют по слову владельца.
   - Ушедший бренд без файла в `data/brands/` в атлас входит. Его конфиг создаётся из одобренного предложения со статусом `gone`.
4. **Мёртвый сайт обходится по Web Archive.**
   - На каждый год с 2018 берётся последняя копия главной и каталога со статусом 200. Обход в ширину идёт по самой поздней такой копии, ссылки остаются привязаны к её timestamp, и архив отдаёт ближайшую копию.
   - Действует `robots.txt` сайта web.archive.org: загружаем мы с него. Архивный `robots.txt` записывается только для сведения.
   - `config.archiveDelayMs` (не меньше 4 секунд) переносится в этот этап. Бюджет страниц тот же.
5. **Что попадает в сырое хранилище:**
   - все загрузки через загрузчик, включая openFDA, iTunes Lookup и `robots.txt`. Одинаковые ответы дедуплицируются по хэшу;
   - каждый шаг редиректа записывается в цепочку журнала, тела ответов 3xx не хранятся;
   - после рендера хранится отрендеренный HTML с пометкой `rendered`;
   - хэш считается по байтам тела. PDF хранится байтами, а не только извлечённым текстом;
   - старые записи `.cache/pages` от тестовых прогонов не импортируются: первый прогон атласа загрузит страницы заново.
6. **Правило про `notes.md`** («прочитай README.md и notes.md сайта перед работой с ним, допиши, что узнал») записывается в `CLAUDE.md` проекта и повторяется в `data/atlas/README.md`. Его выполняют сессии агентов, а не LLM конвейера.
